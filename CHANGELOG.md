## [Unreleased]

### Changed

- Remote workspace helpers are provider-neutral and opt-in (catalog#29, `docs/workspace-providers.md`). The `workspace` profile used to install a GitLab-named git credential helper and `profile.d` file for `workspace_gitlab_host` (default `gitlab.com`) on every run. Now `workspace_git_auth_helper_enabled` (default `false`) installs `/usr/local/bin/git-credential-workspace`, wired in `/etc/gitconfig` for `workspace_git_host` only, which runs `<workspace_external_auth_binary> external-auth access-token <workspace_external_auth_provider>` per request. With the defaults nothing that talks to a workspace service is installed, and a plain SSH workspace needs no setting. When no token can be had the helper says why in one line on stderr and exits 1, never showing the token or the client's output; it refuses output that is not a single token. `workspace_login_env` and `workspace_login_env_unset` replace the fixed `GITLAB_HOST`/`GITLAB_TOKEN` lines. `tasks/validate-config.yml` stops the run when the enabled helper lacks its host, provider, client or user name, or when one of them, or an environment name or value, is not safe in a shell script or `/etc/gitconfig`. Behaviour change: a workspace that relied on the old helper must set `workspace_git_auth_helper_enabled: true`, `workspace_git_host` and `workspace_external_auth_provider`; the old files and their `/etc/gitconfig` entry are removed. `tests/test_workspace_credential_helper.py` (new `workspace-helper` CI job) runs real git against a loopback server and a stand-in workspace service for success and each token failure. Builds on the design of the closed !176.
- The role checks its public configuration before it changes anything (catalog#31, `docs/configuration.md#validation`). `roles/*/meta/argument_specs.yml` types every public variable and lists the allowed values of the enums. The new `tasks/validate-config.yml` (tag `validate`, runs under any `--tags`) re-checks that spec once `local-vars.yml` has loaded. It then checks list and mapping shapes, `https://` URLs, SHA-256 checksums, fingerprints and absolute paths, and the settings an enabled integration needs (Coder, kiosk, missionctl, focuspass, Keycloak, WeeChat Teams, Jellyfin, fleetd, Wi-Fi, PIA). It reports every problem in one message that names the variable, its value and what is allowed. Secrets show as `$REDACTED$` or `(hidden: no_log value)`. StreamStack and Sunshine variables are only type-checked. Behaviour change: a configuration that used to fail part-way through a run, or that a later task quietly coerced (a comma string as a list, for example), now stops at the start and nothing changes. The new `config-validation` CI job runs every example, every hardware and workstation profile pair and the cases in `tests/config_validation/`. `tests/test_argument_specs.py` keeps the spec in step with `docs/reference.md`.
- Dependency-complete release SBOM (catalog#21, `docs/sbom.md`, [decision 0006](docs/decisions/0006-release-sbom.md)). The `sbom` job now writes CycloneDX 1.6 with `catalog-tools sbom` (replacing `scripts/build_collection_sbom.py`): the artifact's files, the `galaxy.yml` dependencies at the version CI resolves, the locked CI toolchain (Python lock, CI collections, job images, `tools/Cargo.lock`), and the runtime package sources, direct downloads and external installers declared in `ci/sbom-sources.yml`, each marked with `curiosity:component-kind`. Generation fails when a role URL or package-manager module is undeclared or a declaration is stale; `check-jsonschema` (now in the CI lock) validates against the vendored CycloneDX schema offline; `catalog-tools sbom --check` fails when a declared dependency is missing. Release tags keep the artifact, SBOM, checksums and toolchain record without expiry (`release_assets`). CI, tooling and docs only; no role change.
- CI toolchain locked (catalog#22): job images are pinned by digest, the Python tooling installs from a hash-checked lock (`ci/requirements.in` to `ci/requirements.txt`, `pip install --require-hashes`), and CI's Ansible collections are pinned in `ci/requirements.yml`. Renovate proposes image, tooling and lock bumps as merge requests, and the `provenance` job records the toolchain in `ci-toolchain.txt` for release evidence. `docs/ci-toolchain.md` has the update path and the two exceptions. CI only; no role change.

### Fixed

- Security: release lookups drop assets without a SHA-256 digest (catalog#28). GitHub reports `digest: null` for assets it never hashed. `get_url` read that as "no checksum", and its `force: false` then kept whatever file sat at the destination, so an installer that does not check the digest itself could install, and keep, an unverified file. `latest-releases.yml` now removes such assets before any installer sees them, and a source left with none stops the run with the existing no-stale-fallback refusal. `docs/quickstarts/restricted-networks.md` now covers the fail-closed behavior for each network failure, which downloads go through a package manager and which through the verified-download cache (and where each cache lives), and an offline workflow that fills that cache by digest. Proxy findings carried over from the first draft of the guide. `tests/test_restricted_network.py` adds unhashed release assets, a vendor checksum server that cannot be reached, a cache filled ahead of time reused with no network, and a wrong file under the right digest name refused.

- Security: vendor-verified downloads for the first dependency register alerts (catalog#171). kubectl, Helm and Go are now checked against the SHA-256 their vendors publish (the `.sha256` next to each binary on dl.k8s.io, the `.sha256sum` on get.helm.sh, the digest in go.dev's JSON index) through the new `tasks/verified-download.yml`, which reads the digest with the release-query retries, downloads nothing without a valid one, and keeps a digest-named cache file only while it matches. Codex installs from the `install.sh` of the latest openai/codex release, checked against its GitHub asset digest, in place of chatgpt.com/codex/install.sh. Claude Code installs the binary named in the release's `manifest.json` after `gpg`, in a GnuPG home holding only the pinned key, verifies the manifest's signature against the pinned Claude Code release key (`files/claude-code-release-key.asc`, fingerprint `claude_native_release_key_fingerprint`), in place of claude.ai/install.sh. SDKMAN! checks out its latest release tag and stops unless the checkout is the commit GitHub's API names for it. velero and kubeseal now track their new repositories (velero-io/velero, bitnami/sealed-secrets). `tests/test_verified_download.py` (fixtures: wrong, missing and malformed digests, tampered or wrongly signed manifests, a moved tag) and `tests/test_verified_download_vendors.py` (the real vendor URLs) run in the new `verified-downloads` job; the register and SBOM sources record the new verification. The PIA installer stays HTTPS-only: PIA publishes no checksum or signature (catalog#171).

- Debian: the `repos` and `packages` steps (catalog#162, catalog#163). `apt_fallback_release` is now chosen per distribution: Ubuntu and its derivatives keep `noble`, Debian uses its own codename. .NET, Azure CLI and MongoDB come from `apt_vendor_repos` through the new `tasks/apt-vendor-repo.yml`. On Debian it uses each vendor's Debian channel (`packages.microsoft.com/debian/<major>/prod`, `repo.mongodb.org/apt/debian <codename>/mongodb-org/<channel> main`). It reads the vendor's Release file first and skips the repository with the reason when the vendor publishes none: on Debian 13 that is Azure CLI, which Debian ships in main. It also removes the noble line an earlier run wrote on Debian. `software-properties-common`, which Debian 13 does not ship and nothing in the role needs, is dropped from the package lists on Debian only (`apt_packages_excluded`), as is `mongodb-mongosh` when MongoDB has no channel for the release. Ubuntu output is unchanged: `tests/test_apt_vendor_channels.py` renders the repository lines and package lists for Ubuntu 24.04 and 26.04 and compares them with a fixture rendered from main before the change, renders Debian 13 against the vendor listings of 2026-11-25, and fails when a `repos*.yml` repository line hard-codes an Ubuntu path or codename without a distribution guard.

### Fixed

- A host without a `display_guard` pin now stops, disables and removes `curiosity-display-guard` (units and binary too), not only its udev rule, resume hook and pin. dm313red shares the `deskmeet-b760` profile with the 8K TV host but has no DP-4: its guard ran all boot logging `output DP-4 not found`, re-probed the displays every few seconds and ran its repair ladder on every hot-plug (Curiosity-Corp/catalog-internal#24).
- CI no longer pulls its Python image from Docker Hub (catalog#97). Every job used `python:3.13-slim` (and `python:<version>-slim` for `research-profile`) from Docker Hub and failed with `429 Too Many Requests` whenever its node did not already have the image cached. The images now come from `public.ecr.aws/docker/library/`, AWS ECR Public's anonymous mirror of the same Docker Official Images: no credentials, no internal registry name in the public repository, and Renovate still tracks the tag.
- Bitwarden desktop installs again from desktop-v2026.11.0 (FocusApiary/infrastructure#928). That release, published 2026-11-19 20:49Z, renamed its debs to `bit-Bitwarden-<v>-amd64.deb` and `oss-Bitwarden-<v>-amd64.deb`. The asset match only accepted `Bitwarden-<v>-amd64.deb`, so the digest assert failed and every workstation's ansible-pull rolled back its update transaction. The match now accepts the official build under either name (`^(bit-)?Bitwarden-<v>-amd64.deb$`) and still never picks the `oss-` or `commercial-` flavour. Both new debs are package `bitwarden` at the release version with the same files, so the install checks are unchanged.
- The hhtest test bed now runs at a low CPU weight (hypervoid/hyperharness#885, #888). A test pinned 150 busy loops to one core and refused every session launch while 90% of the CPUs were idle. The `user-<uid>.slice` drop-in gains `CPUWeight=20` (`hhtest_cpu_weight`, systemd's default is 100), so test hogs lose every contended core to real sessions. No core pinning; memory, task and CPU-quota caps are unchanged.
- `/tmp` no longer fills with leaked Chromium extension unpack folders (#155). Headless Chrome runs with a fresh profile exit before a policy-forced extension finishes installing and leave `/tmp/scoped_dir*/CRX_INSTALL` behind (25-120 MB each). On an agent workstation that reached the owner's per-user `/tmp` quota (80% of the tmpfs) in hours, before the 85% pressure check acted, and an ansible-pull failed with `Disk quota exceeded`. With `tmp_hygiene_enabled`, the new `curiosity-tmp-short-age.timer` runs `systemd-tmpfiles --clean` hourly on `/etc/curiosity/tmp-short-age-tmpfiles.conf` (`e /tmp/scoped_dir* - - - 6h`). It removes only contents whose timestamps are all older than the age and that no process has locked, and it is kept out of `tmpfiles.d` so the emptied folders still age out with `/tmp`. New variables: `tmp_hygiene_short_age_paths` (default `[/tmp/scoped_dir*]`, empty turns it off), `tmp_hygiene_short_age` (`6h`), `tmp_hygiene_short_age_interval` (`1h`) and `tmp_hygiene_short_age_config_path`. `tests/test_tmp_hygiene.py` runs the real `systemd-tmpfiles` on a scratch tree.
- Ziti health check could never find the tunneler (catalog#149). Under systemd, `ziti-edge-tunnel` (installed at `/opt/openziti/bin`) is not on PATH, so `curiosity-ziti-health` failed every two minutes with `cannot run ziti-edge-tunnel: [Errno 2]` and never checked anything (771 failures on deskmeet1 since 2026-11-04). The script now resolves the binary from `ZITI_HEALTH_TUNNEL_BIN`, else PATH, else `/opt/openziti/bin/ziti-edge-tunnel`, and the unit sets it from the new `ziti_health_check_tunnel_bin` default. A binary that cannot be found fails the check with one clear line naming the places searched; nothing is restarted.
- PIA port forwarding no longer sticks to a server without a port API (catalog#148). On 2026-11-04 the tunnel registered with Toronto `Server-10996-8a`, which refused connections on 19999, so no port was ever bound. `curiosity-pia-tunnel up` now treats a port API that does not answer (curl 7/28) as a dead server, remembers it for six hours in `/run/curiosity-pia-tunnel/pf-unreachable.json` and rebuilds on another port-forwarding server (up to four per rebuild; the last tunnel stays up without a port), and `bind` moves the tunnel the same way when its server stops answering. A refusal by PIA itself is not treated as a dead server.

### Added

- Opt-in Fleet agent (`fleetd_enabled`, default `false`): `tasks/fleetd.yml` installs a site-built fleetd package from `fleetd_package_base_url` only after verifying the detached Notation signature on its `SHA256SUMS` (pinned Notation v2.0.0-alpha.1, trust store holding only `fleetd_signing_certificate`) and taking the package checksum from that verified list. Before the install it writes `/etc/curiosity/device-class` and `/etc/curiosity/registry-id` and puts the enroll secret in place as a root-only 0600 `ORBIT_ENROLL_SECRET` env file loaded by an orbit drop-in (delivered out of band or written with `no_log`; the role checks it without reading it), since the package carries only Fleet's placeholder and starts orbit at once. A recipe stamp reinstalls when the recipe changes under the same orbit version. With fleetd on, `site.yml` post_tasks write the converge stamp `/var/lib/curiosity/converged.json` after every complete run. No server, package host or secret is in the repository. `tests/test_fleetd.py` pins the order and renders the real expressions.
- Declarative retirement of system services and files: `workstation_system_masked_units` and `workstation_removed_paths` (both default `[]`, site values in `/etc/ansible/local-vars.yml` or protected inventory). `tasks/system-retirement.yml` stops and disables each listed unit, removes its target links, converges the unit path to the native `/dev/null` mask and reloads systemd, deletes each listed path, then fails the run (tripwire) if a listed unit is not masked or is running, or a listed path exists. Needed because `systemctl disable` without `--now` leaves a unit running until reboot and `Wants=` or needrestart's automatic restart brings it back; this is how a retired service stack kept running on a workstation for two weeks while recorded as "disabled". `tests/test_system_retirement.py` renders the real validation and tripwire expressions.
- Removing Chromium-family extensions per host (mrh/me#11): `chromium_removed_extensions` (default `[]`) lists Chrome store ids; `tasks/collaboration.yml` writes a root-owned `25-removed-extensions.json` (`ExtensionSettings`, `installation_mode: removed`) for each installed Chrome, Edge and Brave and deletes it when the list is empty. ### Changed

- Organization-specific hostnames, CA bundles, and deployment assumptions were
  removed from the tracked baseline.

  control plane before installers execute, so a failed prerequisite cannot
  leave user-scoped CLIs such as Codex stale.
- User-scoped npm and AI refreshes run before binary installers and are kept out
  of binary rollback, so unrelated installer failures cannot undo them.
- Coder, Keycloak, Ziti, Sunshine, chat, and profile cleanup remain opt-in.

### Fixed

- Google Chrome and other Secret Service clients hung on every page load in
  console (`startx`) sessions, such as the pinned VT sessions on DeskMeet1,
  while the same account worked under LightDM. Two causes: `/etc/pam.d/login`
  never unlocked the user's gnome-keyring "login" collection, and the systemd
  user / D-Bus activation environment kept the LightDM greeter's `DISPLAY` (or
  none), so the keyring unlock prompt could not be shown. While
  `minimal_desktop_pinned_vt_sessions` is non-empty the role now installs
  `libpam-gnome-keyring` and adds `auth optional pam_gnome_keyring.so` and
  `session optional pam_gnome_keyring.so auto_start` to `/etc/pam.d/login`
  (`optional`, so a keyring failure never blocks login; removed when no VT is
  pinned), and the Openbox autostart runs
  `dbus-update-activation-environment --systemd` for `DISPLAY` and
  `XAUTHORITY` first thing. Auto-unlock still requires the keyring password to
  match the account's login password.
- The autostart screen-lock harness tests no longer time out under full-suite
  load: the two worst-case handoff paths take ~11 s against a 15 s
  `subprocess.run` timeout, so the timeout is now a 60 s hang guard (#80).
- The minimal desktop's tint2 panel config set `panel_background_id = 1` before
  any background block existed and used options tint2 17 rejects
  (`taskbar_name_active_color`, `taskbar_name_color`, `task_icon_size`). tint2
  17.0.1 (Ubuntu 26.04) segfaulted at startup, so every catalog-managed Openbox
  session had no panel, taskbar or tray. The role now ships valid layouts, and
  the Openbox autostart starts tint2 with that config and replaces an existing
  panel on the same display instead of stacking a second one.
- User-systemd masking tolerates declared units that are absent on the host
  ("Could not find the requested service").
- Pinned VT sessions keep their getty drop-ins: the stale-drop-in cleanup used
  a `'\1'` backreference inside a Jinja literal (U+0001) and removed every
  drop-in it had just written.
- pipx virtualenvs whose base interpreter was removed (distro Python upgrade or
  a home copied from another host) are rebuilt with `pipx reinstall-all`
  before managed pipx installs (`pipx_repair_python`). The user-systemd policy
  test now runs under pytest in CI instead of as a no-op script.
- `/opt/science-venv` built on a Python minor the distro has since replaced
  (3.13 on hosts upgraded to Ubuntu 26.04's 3.14) is rebuilt with
  `python3 -m venv --clear` when its interpreter cannot import pip. The old
  `creates: bin/activate` guard kept the stale venv and every science pip task
  failed, rolling back the whole update transaction.
- Microsoft 365 CLI entry points (`m365_cli_command_links`) are made executable
  after each refresh. `@pnp/cli-microsoft365` publishes `dist/index.js` as
  0644 and npm 12.2 installed it unchanged, so `m365` failed with permission
  denied and the post-update healthcheck rolled the transaction back.
- Sunshine package selection follows the host release and architecture and the
  current upstream asset names (`sunshine_<version>-1+ubuntu26.04_amd64.deb`,
  `+debiantrixie`), with the older `sunshine-ubuntu-24.04-amd64.deb` form still
  accepted. The hard-coded 24.04 name no longer exists upstream, so enabled
  hosts could not install or upgrade Sunshine, and a 24.04 build on 26.04 fails
  to load `libminiupnpc.so.18`.
- Update rollback restores symlinked launchers as symlinks. The pre-update
  snapshot followed links, so a rollback replaced `/usr/local/bin/aws` (a link
  into `/usr/local/aws-cli`) with a copy of the PyInstaller binary that could
  not load its bundled `libpython`, and the next pull failed the aws
  healthcheck. Symlinks are now recorded with `link_target`, skipped by the
  snapshot, and re-linked on rollback.
- `curiosity-display-setup` only considers modes with the aspect ratio of the
  output's preferred mode. UHD panels also list the larger DCI 4096x2160
  (17:9) mode, and choosing by area alone switched a 16:9 display to it.
- `/tmp` hygiene excludes `/tmp/.ziti`, where `ziti-edge-tunnel` keeps its IPC
  and event sockets for the life of the process. A cleaner that removed old
  sockets and then the empty directory left a running tunneler unreachable
  over IPC, so tunnel health metrics failed on every run.
- Vendor APT signing keys (GitHub CLI, Microsoft, Google Cloud, Google Chrome,
  1Password, Brave, MongoDB, NodeSource, OpenZiti, Mozilla) were fetched once
  behind `creates:` or a non-forcing download and never refreshed, so a vendor
  key rotation left hosts failing `apt update` with `NO_PUBKEY` (GitHub CLI
  key `5612B36462313325`). `tasks/apt-keyring.yml` now re-downloads every key
  on each run with retries, dearmors only ASCII-armored sources, verifies the
  OpenPGP content (and the pinned fingerprint where one is configured) before
  replacing the keyring, and reports `changed` and refreshes the apt cache
  only when the vendor content differs. Keyring paths and `signed-by=` lines
  are unchanged; staging copies live in `apt_keyring_staging_dir`.
- Hosts bootstrapped with the upstream OpenZiti install script kept
  `/etc/apt/sources.list.d/openziti.list` with
  `signed-by=/usr/share/keyrings/openziti.gpg`; the catalog's own OpenZiti
  entry in the same file then made apt fail with "Conflicting values set for
  option Signed-By". The upstream-form line is now removed before the catalog
  entry is added, and the orphaned `openziti.gpg` keyring is deleted only when
  nothing in `/etc/apt` still references it.
- Post-update healthchecks no longer roll the update back for applications
  whose feature is disabled on the host. The checks are opportunistic (any
  contract whose executable exists is run), so a stale, broken
  `/usr/bin/sunshine` on a host with `sunshine_enabled: false` failed every
  pull, rolled the whole transaction back, and wrote an hour-long quarantine
  that blocked unrelated updates. Application contracts accept an optional
  `enabled_when: <variable name>`; the Sunshine, Coder, aws, glab, and Codex
  contracts name `sunshine_enabled`, `coder_cli_enabled`, `cloud_clis_enabled`,
  and `codex_standalone_enabled`. A failing check for a disabled application is
  logged as a warning and recorded as `healthcheck_warnings` in the run
  manifest; contracts for enabled applications, or without a condition, still
  fail hard.

## Security and supported versions

Only the latest released collection and the default branch receive routine
security fixes ([`SECURITY.md`](SECURITY.md)). No security advisory has been
published yet. When one is, the release that fixes it lists it under `### Security`
with the fixed and affected versions and a link to the advisory, and the advisory
names the same versions (see [`docs/vulnerability-response.md`](docs/vulnerability-response.md)).
